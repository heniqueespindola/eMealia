# Research: Despensa (Inventário de Ingredientes)

## Questão de Pesquisa
Como estruturar o ecrã da despensa (`app/(tabs)/pantry.tsx`) e o hook `usePantry`, incluindo agrupamento por categoria de `pantry_items` (e se é necessária uma coluna `categoria` no schema), a integração do scanner de código de barras (`expo-camera`) com a Open Food Facts API, a partilha de ingredientes seleccionados entre a despensa e o ecrã de pesquisa (botão "cozinhar agora"), e a aplicação do limite de 20 itens do plano Grátis vs. ilimitado no Premium?

## Sumário
O ecrã `pantry.tsx` hoje é apenas um stub, mas grande parte da infraestrutura já existe em estado parcial e inconsistente: um `usePantry.ts` que faz CRUD directo no Supabase (ignorando as queries já prontas em `@emealia/supabase`), um `pantryStore.ts` Zustand órfão (zero consumidores), componentes de ingrediente reaproveitáveis do ecrã de pesquisa, e um limite de plano (`LIMITS.free.pantry_items = 20`) já definido em `@emealia/config` mas nunca lido em código nenhum. Não existe coluna `categoria` no schema nem em nenhuma migration (a pasta `supabase/migrations/` está vazia — todas as alterações de schema vivem directamente, de forma idempotente, em `supabase/schema.sql`); não existe integração com Open Food Facts em lado nenhum do código (`expo-camera` já está instalado); e não existe nenhum padrão estabelecido no repo para verificar `profiles.plano` antes de uma acção (nem no cliente nem nas Edge Functions) — isto terá de ser criado de raiz para esta feature.

## Padrões de Implementação Existentes

**Hook CRUD "bem alinhado" (a seguir para reescrever `usePantry`)** — `apps/mobile/src/hooks/useProfile.ts`:
```ts
import { useEffect } from 'react';
import { supabase } from '@/lib/supabase';
import { getProfile } from '@emealia/supabase';
import { useProfileStore } from '@/stores/profileStore';

export function useProfile(userId: string | undefined) {
  const profile = useProfileStore((s) => s.profile);
  const loading = useProfileStore((s) => s.loading);

  useEffect(() => {
    if (!userId) {
      useProfileStore.getState().setProfile(null);
      useProfileStore.getState().setLoading(false);
      return;
    }
    const current = useProfileStore.getState().profile;
    if (current && current.id === userId) {
      useProfileStore.getState().setLoading(false);
      return;
    }
    useProfileStore.getState().setLoading(true);
    getProfile(supabase!, userId).then(({ data, error }) => {
      if (error) console.error('[useProfile] getProfile falhou:', error);
      useProfileStore.getState().setProfile(data ?? null);
      useProfileStore.getState().setLoading(false);
    });
  }, [userId]);

  return { profile, loading };
}
```
Padrão: hook lê/escreve num Zustand store partilhado, importa funções de query cruas de `@emealia/supabase`, erro tratado com `console.error` + fallback (nunca lança), loading é boolean no store.

**Estado actual (desalinhado) de `usePantry.ts`** — CRUD directo, sem store, sem `@emealia/supabase`:
```ts
export function usePantry(userId: string) {
  const [items, setItems]   = useState<PantryItem[]>([]);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    async function fetch() {
      const { data } = await supabase
        .from('pantry_items').select('*').eq('user_id', userId)
        .order('created_at', { ascending: false });
      setItems(data ?? []);
      setLoading(false);
    }
    fetch();
  }, [userId]);

  async function add(item: Omit<PantryItem, 'id' | 'created_at'>) {
    const { data } = await supabase.from('pantry_items').insert(item).select().single();
    if (data) setItems((prev) => [data, ...prev]);
  }

  async function remove(id: string) {
    await supabase.from('pantry_items').delete().eq('id', id);
    setItems((prev) => prev.filter((i) => i.id !== id));
  }

  return { items, loading, add, remove };
}
```

**Mecanismo actual de "usar despensa" na pesquisa** (a generalizar/reaproveitar para "cozinhar agora"):

```ts
// apps/mobile/src/hooks/useRecipeSearch.ts:48-58
function usarDespensa(pantryItems: PantryItem[]) {
  setIngredients((prev) => {
    const next = [...prev];
    for (const item of pantryItems) {
      if (!next.some((i) => i.toLowerCase() === item.nome.toLowerCase())) {
        next.push(item.nome);
      }
    }
    return next;
  });
}
```

## Tabelas/Queries Supabase Relevantes

**`pantry_items` (schema.sql:43-60)** — sem `categoria`, sem CHECK constraints além de `NOT NULL` em `nome` e FK `NOT NULL` em `user_id`:
```sql
CREATE TABLE IF NOT EXISTS pantry_items (
  id          uuid        DEFAULT gen_random_uuid() PRIMARY KEY,
  user_id     uuid        REFERENCES profiles(id) ON DELETE CASCADE NOT NULL,
  nome        text        NOT NULL,
  quantidade  text,
  barcode     text,
  expira_em   date,
  created_at  timestamptz DEFAULT now()
);

ALTER TABLE pantry_items ENABLE ROW LEVEL SECURITY;

DROP POLICY IF EXISTS "pantry: só o próprio" ON pantry_items;
CREATE POLICY "pantry: só o próprio"
  ON pantry_items FOR ALL USING (auth.uid() = user_id);

CREATE INDEX IF NOT EXISTS pantry_items_user_id_idx ON pantry_items(user_id);
```

**`profiles.plano` (schema.sql:12)** — único campo de plano, sem coluna de limite dedicada:
```sql
plano text DEFAULT 'free' CHECK (plano IN ('free','premium_monthly','premium_annual')),
```

**Migrations** — `supabase/migrations/` existe mas está **vazia**. Todo o schema vive em `supabase/schema.sql`, escrito de forma idempotente (`CREATE TABLE IF NOT EXISTS`, `DROP POLICY IF EXISTS` + `CREATE POLICY`, `CREATE INDEX IF NOT EXISTS` — comentário no topo do ficheiro: `-- Versão idempotente: pode ser corrida múltiplas vezes sem erros`). Não há convenção de nomeação de migrations neste repo — uma futura coluna `categoria` seria adicionada directamente em `schema.sql` com `ALTER TABLE pantry_items ADD COLUMN IF NOT EXISTS categoria text ...`, ou seria necessário criar a convenção de migrations do zero.

## Questões em Aberto

1. **Coluna `categoria`**: não existe no schema, nas migrations (inexistentes), nem no tipo `PantryItem`. Precisa de decisão em `/plan`: (a) adicionar `categoria text` a `pantry_items` via `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` em `schema.sql` (abordagem mais simples, dado o padrão idempotente já usado), ou (b) inferir categoria no cliente a partir de heurística de nome/dados da Open Food Facts sem persistir. Adicionar coluna parece mais alinhado ao padrão existente (schema idempotente, sem sistema de migrations formal) e evita lógica de inferência frágil.
2. **Partilha de ingredientes despensa → pesquisa ("cozinhar agora")**: hoje não há mecanismo formal — `search.tsx` faz um fetch próprio de `usePantry(user.id)` e injecta via `usarDespensa()`. Existe um `pantryStore.ts` Zustand pronto mas não usado por ninguém. Decisão em `/plan`: usar `pantryStore` como fonte única (populado pelo ecrã da despensa) e ter tanto `pantry.tsx` como `search.tsx` a lerem dele, ou navegar com params (`router.push({ pathname: '/(tabs)/search', params: { ingredientes: [...] } })`). Dado que Expo Router serializa params como strings, o store partilhado parece a opção mais limpa para uma lista de ingredientes.
3. **Reconciliação de `usePantry.ts`**: hoje ignora as queries já existentes em `@emealia/supabase` (`getPantry`, `addPantryItem`, `deletePantryItem`, `addPantryItems`) e usa `useState` local em vez do `pantryStore` órfão. Decidir em `/plan` se se reescreve `usePantry` para seguir o padrão de `useProfile` (store + queries partilhadas) — parece necessário de qualquer forma para resolver a questão nº2 acima.
4. **`updatePantryItem` em falta**: precisa de ser adicionado a `packages/supabase/src/queries/pantry.ts`, seguindo o padrão `.update(...).eq('id', id).select().single()` já usado em `updateProfile`.
5. **Enforcement do limite de 20 itens**: não há Edge Function no caminho de escrita da despensa (é client-direct para `pantry_items`), e RLS não impõe contagens. Confirmar em `/plan` que o gate é 100% client-side (ler `profile.plano` via `useProfile`/`profileStore`, comparar `items.length` com `LIMITS[plano === 'free' ? 'free' : 'premium'].pantry_items` antes de chamar `add`), sabendo que isto é contornável por um cliente malicioso (aceitável para MVP dado que não há precedente de enforcement server-side em nenhuma outra feature do repo, mas vale confirmar explicitamente que este risco é aceite).
6. **Formato exacto da resposta da Open Food Facts** para o endpoint de produto por barcode — não há precedente no repo; confirmar em `/plan` os campos exactos a mapear (nome do produto, eventual categoria) a partir da resposta JSON real da API v2.
7. **Autocomplete de nomes comuns na despensa**: `useIngredientAutocomplete.ts` já existe e chama a Edge Function `autocomplete-ingredients` (Spoonacular, cache 1h) — confirmar em `/plan` se se reutiliza tal como está (nomes provavelmente em inglês/normalizados pela Spoonacular) ou se se cria uma lista estática pt-PT separada para a despensa, dado que os nomes na despensa devem idealmente estar em português para o utilizador.
8. **`Card`/`Badge` em falta em `src/components/ui/`**: nenhum dos dois existe; precisam de ser criados (ou usar `View`/`Pressable` inline seguindo o estilo de `IngredientChip`/`Pill`) para os cards de item da despensa e o badge de alerta de validade.
